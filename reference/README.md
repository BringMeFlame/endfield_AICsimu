# reference/

配方 + 物品系统的数据准备产物，不是运行时代码，`src/` 下的任何模块都不
依赖这个目录（等真正把配方/物品接入设备逻辑时，会把核对完的数据转成
`src/data/items.js`/`src/data/recipes.js`，那之后这里的东西就是历史存档）。

## 文件

- **`items_recipes_template.xlsx`** —— 主数据文件，人工核对/填写的入口，
  三个 sheet：
  - 「物品」：199 个物品 id + 中文名 + portType（固体/流体）
  - 「设备槽位与机器归属」：`facilities.js` 45 条设备记录的槽位数（固体/
    流体输入输出各一个数字，设备固有属性，和现有端口数量无关）+ 候选
    machineId 映射（wiki 抓取的 18 台机器 id，部分置信度低，已在表里标注）
  - 「配方」：305 条配方（wiki 抓取，最多 2 进 2 出）+ 所属 facility_id +
    环境条件（惰气/酸气环境覆盖判定、固气/液气转化机的催化剂消耗需求，
    见下方"设计要点"）
  - 第一个 sheet「说明」里有配色图例和填写说明，改这份表之前先看那个
- **`item_ids.json`** —— 从 xlsx「物品」sheet 导出的 `{id, name}` 精简列表，
  给 `scripts/fetch-item-icons.*` 当输入用。**这是快照，不会跟着 xlsx 自动
  同步**——以后 xlsx 里的物品增删了，这份 json 要手动重新导出一次（现在
  是我用一次性脚本导的，还没写成可重复跑的同步工具，属于已知的手动步骤）。

## 数据来源与已知缺口

原始 wiki 抓取数据（`recipes.txt`/`item_list.txt`，305 条配方原始 JSON +
物品中文名清单）在另一个分支 `claude/infrastructure-simulator-items-recipes-0rag21`
的 `reference/raw/` 下，**还没合并进这条分支**——目前这里只有从那份原始
数据加工出来的 xlsx 模板，没有原始抓取文件本身。要不要把 `raw/` 也合过来
留档，还是保持现状（原始数据只在那条分支上留一份），需要再确认一下。

## 设计要点（供后续接入 `src/` 代码时参考，不是这份数据本身的字段）

- 槽位数是设备固有属性，和 `facilities.js` 现有的端口数量是两回事，不能
  按端口 id 一一对应。
- 惰气/酸气环境：气体散布机需要接入速率 ≥ 某个数值的对应气体才会以自身
  为中心投射方形范围；目标设备要**完全**被覆盖才算满足（对比现有电力
  供电覆盖判定是"部分覆盖即算通电"，可以复用同一套 `computePowerRangeRects`
  代码结构，只是覆盖条件从"部分"改成"完全"）。未满足时复用现有"未通电"
  警告图标+浮窗框架，文案"气体环境未满足"。
- 固气/液气转化机的催化剂（额外接一路液化息壤/息壤气）**是真正被消耗的
  输入**，不是旁路条件判断；UI 上要单独给一个槽位展示，不能藏在配方
  固定输入槽背后。未接入时同样复用警告图标框架，文案"未接入液化息壤/
  息壤气"。
- 本期明确不做速率计算（传送带/管道网络级产能推算），配方数据里的
  `baseTime`/流速门槛这类数字暂时不接入任何判定逻辑。
